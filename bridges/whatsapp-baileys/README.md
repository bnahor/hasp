# whatsapp-baileys bridge

A small local bridge between WhatsApp (via [Baileys](https://github.com/WhiskeySockets/Baileys),
`@whiskeysockets/baileys@7.0.0-rc14`, MIT) and the hasp gateway. It runs as a linked device
on the owner's own account, writes every real-time incoming message to an append-only JSONL
log, and serves a loopback HTTP API that `crates/hasp-gateway/src/adapters/whatsapp.rs` reads.

## Read this first: terms of service and ban risk

- Baileys is unofficial and not affiliated with WhatsApp. It connects as a Linked Device.
  Automating a personal account breaches WhatsApp's Terms of Service, and the account can be
  banned.
- Low-volume, one-to-one use by the owner is the lowest risk. Never use this for bulk,
  unsolicited or automated messaging to other people.
- **If losing the WhatsApp account would hurt, use a secondary number** for the assistant.

## Setup

Requires Node 22.18 or newer (the source is TypeScript run directly with Node's type
stripping; Baileys itself needs Node 20+).

```sh
cd bridges/whatsapp-baileys
npm install
# a long random bearer token, readable only by you
umask 077 && openssl rand -hex 32 > ~/.config/hasp/whatsapp-bridge.token
chmod 600 ~/.config/hasp/whatsapp-bridge.token
```

Environment:

| var | default | meaning |
|---|---|---|
| `BRIDGE_TOKEN_FILE` | (required) | file with the bearer token; must be mode 0600 |
| `BRIDGE_PORT` | `8790` | port on 127.0.0.1 |
| `BRIDGE_DATA_DIR` | `./data` | `events.jsonl`, `lid-map.json`, `messages.jsonl`, `auth/` |
| `BRIDGE_LOG_LEVEL` | `warn` | Baileys log level (stderr) |

```sh
BRIDGE_TOKEN_FILE=~/.config/hasp/whatsapp-bridge.token BRIDGE_DATA_DIR=~/.local/share/hasp/whatsapp npm start
```

## Pairing is a manual step for the owner

On first start (no credentials in `<data>/auth`) the bridge prints a QR code to **stderr**.
The account owner scans it by hand on their phone: WhatsApp > Settings > Linked devices >
Link a device. Nothing in this bridge scans the QR, requests a pairing code, or links an
account by itself. After pairing WhatsApp asks for a restart (code 515); the bridge
reconnects on its own.

Credentials live in `<data>/auth` (Baileys' `useMultiFileAuthState`). Upstream warns that
this store is not meant for production; for one personal account it is tolerable, but keep
the directory on a durable disk, back it up, and keep it private (it is the account login).

Reconnect rules: reconnect with backoff on close; 515 reconnects immediately; **401 logged
out** stops (delete `<data>/auth` and pair again); **440 connection replaced** stops instead
of fighting the other session in a loop (restart the bridge to take over); 403 also stops.
While stopped the HTTP API stays up: `/events` still serves the log, `/send` returns 503.

## HTTP API (127.0.0.1 only, `Authorization: Bearer <token>` on every route)

- `GET /events?after=<seq>&wait=<s>`: long poll, returns as soon as there are events with
  `seq > after`, or after `wait` seconds (capped at 30). At most 500 events per reply.
  `{"events":[...], "next": <highest seq returned, or after>}`.
- `POST /send {"jid","text","quotedId"?}`: 200 `{"id"}`; 503 not connected (nothing sent);
  504 handed to the socket but no result in time; 400 bad input; 500 other socket errors.
- `GET /health`: `{"connected", "me": {"pn", "lid"}, "lastEventSeq"}`.

Event fields: `seq, chat, id, fromMe, sender, pushName, text, quotedId, timestamp, isGroup,
attachments[{id, kind: voice|audio|photo|video|document, mime, name, size}]`.
`test/fixtures/events.json` holds real sample responses (generated by the tests) for the Rust
adapter tests.

The owner's "Message yourself" chat can arrive as either their phone-number JID or their LID.
The bridge learns LID/PN pairs (from `remoteJidAlt`/`participantAlt`, `lid-mapping.update`
and the account's own creds), persists them in `lid-map.json`, and always reports the self
chat as `me.pn` (or `me.lid` if no PN is known). Configure the gateway's self JIDs from
`/health`.

## Durability

- `events.jsonl` is append-only, one event per line, fsynced before the event is visible.
- `(chat, id)` is deduplicated, also across restarts.
- A torn last line is moved to `events.jsonl.torn-<offset>` and the log truncated to the
  valid prefix. Corruption anywhere else stops the bridge with an error; fix it by hand.
- `messages.jsonl` is a bounded cache (2000) of raw recent messages used for quoting and for
  Baileys' `getMessage` retries. It is a cache; losing it only loses quotes of old messages.

## What this bridge does NOT do

- No buttons, lists or interactive messages (unsupported for personal accounts; use
  numbered text replies).
- No history import: only `messages.upsert` with type `notify` is logged; `append`
  (history/backfill) is ignored, and full history sync is off.
- No media download yet (attachments carry the message id for a later download endpoint).
- No reactions, edits, deletes, read receipts, presence, polls or stickers in the event stream.
- No status/stories or channels (newsletters).

## Development

```sh
npm test          # node --test, ~1 s; uses a fake JID shim and never loads Baileys
npm run typecheck # tsc --noEmit
UPDATE_FIXTURES=1 npm test   # regenerate test/fixtures/events.json
```

Layout: `src/normalize.ts` (pure WAMessage to event mapping, JID helpers via an injected
shim), `src/log.ts` (event log), `src/store.ts` (LID map, message cache),
`src/server.ts` (HTTP), `src/socket.ts` (Baileys wiring), `src/index.ts` (entry; the only
place Baileys is imported at runtime).
